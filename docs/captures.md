# Fixture captures

Every capture in `captures/` is generated by `scripts/make-captures.ts`. The protocols are
synthetic and specified here, which is what makes the test suite meaningful: every assertion
compares an inference against a documented layout instead of another inference.

Regenerate with `npm run captures`. Output is deterministic — same bytes on every run.

---

## `binary-session.pcap` / `.pcapng`

TCP, `10.0.0.10:41000` → `10.0.0.20:7401`. Eight request/response rounds, plus a ping/pong and
an error exchange. Both directions carry 10 messages.

```
offset  size  field
0       2     magic      0xa5 0x5a
2       1     length     total message length, big endian, checksum included
3       2     sequence   little endian, +1 per message per direction
5       1     type       0x01 ping, 0x02 pong, 0x10 read, 0x11 data, 0x20 error
6       n     payload    ASCII, e.g. "temperature=21.75"
6+n     2     checksum   crc16/modbus over bytes [0, 6+n), little endian
```

Messages are split across TCP segments, with one out-of-order segment pair and one
retransmission per exchange. The `.pcapng` file is the same traffic in a different container,
so the test suite can assert both parsers produce identical streams.

Expected inference: length-prefix at offset 2 with bias 0, six fields, checksum
`crc16/modbus` matching 10/10, `type` read as a two-value enum, and the printable run `uptime`
located at payload offset 0.

## `binary-session-v2.pcap`

The same protocol with the type byte removed:

```
offset  size  field
0       2     magic
2       1     length
3       2     sequence
5       n     payload
5+n     2     checksum
```

Its purpose is `protopath diff`: the type byte's disappearance has to show up as a layout change,
not as a silent reinterpretation. The header ends after `sequence` and the ASCII payload begins at
byte 5; the tool cannot know a field was removed, only that the layout moved.

## `text-session.pcap`

TCP, `10.0.0.10:43000` → `10.0.0.20:7402`. Eight line-command exchanges:

```
PING / PONG
GET temp / DATA 23.5
SET led on / ACK 0
GET uptime / DATA 40213
SET mode auto / ACK 0
GET serial / DATA SN-0042
GET bogus / ERR unknown key
PING / PONG
```

Framing is a single-byte terminator `0x0a`. Field inference collapses to one `text` field, which
is the correct answer for a text protocol: the structure is in the words, not in byte offsets.
Labels come from the first word (`verb=GET`).

## `sensor-udp.pcap`

UDP, `10.0.0.30:50000` → `10.0.0.40:7403`. Twenty-four 12-byte datagrams, one direction only.

```
offset  size  field
0       2     origin      0xaa 0x55
2       1     state       0x10 or 0x11
3       1     sequence    +1 per datagram
4       2     temperature big endian, signed, centi-degrees
6       2     humidity    big endian
8       1     node id     3
9       3     reserved    zero padding
```

Framing is recovered as a start-marker `0xaa55`. This fixture exists to prove the UDP path: no
session, no sequence numbers, datagrams simply concatenated in arrival order — which is exactly
why the sequence counter is worth detecting.

Expected inference: start-marker `0xaa55`, `magic`, `type` at the state byte, `sequence` at byte 3,
`payload` for the rest. `reserved` padding is what stops the header from extending further.

## `custom-crc.pcap`

TCP, `10.0.0.50:44000` → `10.0.0.60:7404`. Ten request/response rounds. The point of this
fixture is that nothing in the checksum catalogue matches it:

```
offset  size  field
0       2     length       total message length - 2, big endian
2       2     sequence     big endian, +1 per message per direction
4       1     type         0x21 request, 0x22 response
5       n     payload      ASCII: a key name outbound, "key=value" inbound
5+n     2     checksum     crc16, poly 0x8f57, init 0x1234, refin/refout, little endian
```

The polynomial and the initial value appear in no published table. Expected inference: the
length-prefix framing, a two-byte counter, and a recovered CRC parameter set matching all ten
messages exactly — including the reflected polynomial `0xeaf1`, which the generator never stores.

Known limitation of this fixture, and the honest behaviour worth keeping: every request carries the
same type byte, so that byte is reported as `reserved` rather than as a `type`. The report says
"identical 0x21 in all 10 messages" and leaves the conclusion to the reader.

Read the derivation in **[crc-recovery.md](crc-recovery.md)**.

## `modbus-session.pcap`

The only capture here that is not synthetic. `scripts/record-modbus.py` runs a pymodbus server, a
pymodbus client and a byte-level TCP proxy that writes what the two libraries exchanged into a
pcap. Fifteen operations, mixed reads and writes, plus one Modbus exception response.

Ground truth is the Modbus/TCP application header from the specification:

```
offset  size  field
0       2     transaction identifier, big endian, +1 per request
2       2     protocol identifier, always 0x0000
4       2     length, big endian, counts unit id and PDU (so total = length + 6)
6       1     unit identifier, 0x01 in this session
7       n     function code, then PDU data
```

protopath recovers exactly that layout in both directions, reports no checksum field, and labels
messages by function code (`type=0x03`, `type=0x10`, …).

Read the full write-up, including the three inference defects this capture exposed:
**[showcase-modbus.md](showcase-modbus.md)**.

Regenerate with:

```console
$ pip install pymodbus
$ python scripts/record-modbus.py captures/modbus-session.pcap
```

These numbers are asserted in `tests/`. If a change to the inference changes them, the test
fails before the README can go stale.
